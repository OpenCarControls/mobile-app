# BLE & pairing

How the app pairs with and talks to the controller over BLE. For the firmware side see the firmware repo's BLE doc. Overall design: [Architecture](architecture.md).

## Pairing & connection model
The device advertises **only** while its pairing button is held. The app never scans outside `PairingWizardScreen`. BLE is implemented with **`flutter_reactive_ble: ^5.4.1`**.

*   **First launch / unpaired:** `AppEntryRouter` shows `PairingWizardScreen`. The user holds the button → the wizard scans → taps Pair → `connectToDevice()` → `discoverAllServices()` → write-probe to the RX characteristic triggers the Android pairing dialog → bond confirmed (write succeeds) → `pairedVehicleProvider.notifier.pair(config)` → the router rebuilds to the dashboard.
*   **Connect retries in the wizard:** `connectToDevice`'s stream does *not* retry: it ends at the first `disconnected` update, and the plugin then disconnects the device itself. An attempt can also end or go quiet right after it starts (mobile-app#52: Android registers a GATT client and closes it at once), which used to leave the wizard on "Pairing…" until its 60 s timeout. The wizard therefore connects through `connectForPairing` (`lib/providers/ble_pairing_connect.dart`): an attempt that ends, errors or stays silent for 15 s before `connected` is cancelled, and a new one starts 0.5 s later (longer than the plugin's 200 ms grace on a disconnect it was asked for), until the pairing window is over. Pre-connect `disconnected` updates are not forwarded; after `connected` the plugin's stream passes through unchanged. The Dart side already disconnects the device when a stream ends on its own (the plugin's `Repeater` runs `disconnectDevice` from its `onCancel`), so no native connector is left behind by that path.
*   **Write-probe bonding:** the wizard writes `[0]` to the app→device (RX) characteristic in a retry loop. Firmware enforces bonding on writes (not CCCD/subscribe), so the first write returns `ATT_INSUFFICIENT_AUTH`, Android shows the dialog, bonds, and the retry succeeds. Config is saved **only** after the write succeeds (bond proven). A `Future.any([write, disconnectCompleter.future])` race prevents hanging if the link drops mid-write.
*   **Subsequent launches:** `bleConnectionProvider` reconnects via `connectToDevice()` (no scan). The stream auto-retries on disconnect; pre-connect `disconnected` events are NOT errors. If the stream itself ends or errors, one retry is scheduled 30 s later; any new connection attempt cancels it. Pull-to-refresh on a dashboard (`BleConnectionNotifier.pullToRefresh()`) is such an attempt: it reconnects at once whenever the paired vehicle uses BLE (`PairedVehicleConfig.usesBle`), even though the transport is still MQTT, and does nothing while already connected or while Bluetooth is off or not permitted. The same applies when post-connect setup fails (MTU, service discovery, missing service or characteristics): the half-set-up link is dropped and a retry is scheduled, since the link staying up would otherwise mean no further `connected` event. The setup belongs to the link that was up when it started: if that link drops, is cancelled (e.g. by a pull) or is replaced meanwhile, the setup stops after its current step instead of going on. Otherwise `discoverAllServices` on the dead link makes Android reconnect outside the `connectToDevice` stream, and the setup reports `BleReady` on a link that never exchanged its MTU, which no retry or pull gets out of.
*   **Device lost the bond:** if the device no longer has this phone's bond (removed with `RemovePairedPhone`/`ClearPairedPhones`, flash erased, or evicted by `max_bonded_phones`) but Android still does, the firmware drops every connection and Android shows no pairing prompt. With the pairing window closed it hangs up within milliseconds, before Android reports `connected`; with it open the link drops with `Authentication Failure` during setup. `BleConnectionNotifier` counts as an early drop an attempt that fails within 5 s without connecting (an out-of-range attempt only fails at the 30 s connection timeout), and a link that drops within 10 s of connecting (including an unusable MTU, but not a missing service or a reconnect the app starts itself). Two in a row set `bleBondLostProvider`; a link that stays up for 10 s, or unpairing, clears it. The dashboards then show `BleBondLostBanner`: forget the device in Android's Bluetooth settings, and an "Unpair and pair again" button that unpairs, which returns to the wizard. Retries carry on meanwhile, in case the drops had another cause.
*   **HTTP debug path** (debug builds only): the wizard offers host/port entry + POST `/pairing` + POST `/pair`; saves config with `transportPreference = http`.
*   **Unpair:** overflow menu on the dashboard → confirmation dialog → `pairedVehicleProvider.notifier.unpair()` → the router returns to the wizard.
*   **`createBond()` is never called** — bonding is driven by the write-probe, not explicit bond requests.
*   **Stale-bond recovery:** if the firmware drops the link after connecting (it had a stale bond, the phone forgot it), `disconnectCompleter` fires and the wizard returns to the "found" step with a warning banner. Firmware clears its entry on that drop; the next Pair tap succeeds normally (the user sees two OS pairing prompts in total).

## BLE specifics
*   **Library:** `flutter_reactive_ble: ^5.4.1`. Singleton in `lib/providers/ble_provider.dart` (`bleProvider`).
*   **Key API:** `ble.connectToDevice(id, connectionTimeout)` stream auto-retries; `discoverAllServices(deviceId)` (void) then `getDiscoveredServices(deviceId)` → `List<Service>` (`.id` is `Uuid`, `.characteristics` is `List<Characteristic>`); `subscribeToCharacteristic(QualifiedCharacteristic)`; `writeCharacteristicWithResponse(char, value: bytes)`.
*   **`QualifiedCharacteristic`** takes `deviceId` (String), `serviceId` (Uuid), `characteristicId` (Uuid). Use `Uuid.parse(uuidString)`.
*   **MTU and fragmentation:** after connecting, the app requests `kBleAttMtu` (247, from `ble.payload` in the contract) and passes the negotiated value to `BleReady.attMtu`. Every write and notification is one chunk, as defined by the contract (`ble.fragmentation` in `transport.toml`, see `contracts/docs/ble-fragmentation.md`): a 2-byte header (byte 0: bit 7 = last chunk, bits 0-6 = chunk index; byte 1: message sequence number) plus up to `MTU - 5` bytes of the message stream, which is the encoded message followed by its CRC-32. The logic lives in `lib/transport/ble_fragmentation.dart` (`splitIntoBleChunks`, `BleReassembler`, `bleCrc32`) and is unit-tested without a device. The app logs a warning when the MTU is below `kBleAttMtu`. Below `kBleMinAttMtu` (including the 0 Android reports when the link dropped during the exchange) the device would drop its messages, so the setup fails and the link is retried.
*   **Receiving:** `BleCarTransport` feeds each notification to a `BleReassembler` and decodes once the last chunk arrives. A gap, duplicate or missing first chunk, a sequence number that changes mid-message, a CRC mismatch, a chunk later than `kBleReassemblyTimeoutMs`, or a message over `kBleMaxMessageBytes` (4096) drops the partial message with a log line; nothing is sent back. There is one transport (and reassembler) per connection, so a partial message never survives a disconnect.
*   **Sending:** `BleCarTransport.send()` splits the encoded message (plus CRC, with an incrementing sequence number) into chunks sized from the negotiated MTU and writes them one at a time with response. Sends are serialised so chunks of two messages never interleave. It throws a `CarTransportException` for an empty or oversized message or an MTU below `kBleMinAttMtu`.
*   Direct reconnect via `connectToDevice(remoteId)` — no scan after pairing. Do **not** treat pre-connect `disconnected` events as failures.
*   **`source_device_id`:** UUID v4 generated on first launch, persisted via `SharedPreferences` (`getOrCreateDeviceId()`), injected as `bleSourceDeviceIdProvider`. Never hardcode it. (The firmware overwrites it with the verified BLE peer address anyway.)
*   `sendBasicCommand()` / `sendAdvancedCommand()` inject `sourceDeviceId` automatically for BLE/HTTP.
*   **RxJava 2 crash fix:** `flutter_reactive_ble` installs no `RxJavaPlugins` error handler, so a link loss while an RxAndroidBle operation is in flight and already disposed would kill the process with an `UndeliverableException`. `OpenCarApplication.kt` sets a global handler that logs and drops an error if it, or anything in its cause chain, is a RxAndroidBle `BleDisconnectedException` or `BleGattException`; anything else takes RxJava's default path and still crashes. The check uses `is` on the classes, not class names, so R8 minification (which renames them) can't break it. `app/build.gradle.kts` declares `rxjava` and `rxandroidble` explicitly, since the plugin doesn't expose them to the app module.
